# Часть 2 — Конвертация модели в ONNX

## 1. Описание конвертации

- **Исходная модель:** sergeyzh/rubert-mini-frida (PyTorch, 32.3M параметров)
- **Формат:** ONNX (Open Neural Network Exchange)
- **ONNX opset:** 14
- **Инструмент экспорта:** torch.onnx.export() с dynamic axes для batch size и sequence length
- **Оптимизации при экспорте:** constant folding
- **Runtime:** ONNX Runtime (CPUExecutionProvider), graph optimization level = ORT_ENABLE_ALL

### Процесс конвертации

1. Загружается PyTorch модель через AutoModel.from_pretrained
2. Создаются dummy входы (input_ids, attention_mask) через токенизатор
3. Модель экспортируется в ONNX с динамическими осями (batch_size, sequence_length)
4. Результат валидируется через onnx.checker.check_model

### Размер модели

| Формат | Размер |
|---|---|
| PyTorch (safetensors) | 123.1 MB |
| ONNX | 123.9 MB |

## 2. Архитектура сервиса

- **Фреймворк:** FastAPI + Uvicorn
- **Библиотека инференса:** ONNX Runtime (onnxruntime)
- **Токенизатор:** HuggingFace AutoTokenizer
- **Post-processing:** Mean pooling + L2 normalization (numpy)
- **Устройство:** CPU
- **Эндпоинты:** такие же как в первой части
  - `POST /encode` — кодирование одного текста
  - `POST /encode_batch` — кодирование батча текстов
  - `GET /health` — healthcheck

## 5. Анализ и выводы

### Латентность одиночных запросов

При ONNX Runtime ускоряются одиночные запросы: медианная латентность снизилась с **8.14 ms до 4.67 ms** за счёт того, что ORT выполняет граф-оптимизации (operator fusion, constant folding) и избегает накладных расходов PyTorch runtime. Значение p99 улучшилось ещё сильнее с 67.20 мс до 11.46 ms, что говорит о более стабильном и предсказуемом времени отклика.

### Батчевая обработка

Для одиночных элементов в батче ONNX быстрее (4.85 мс против 7.90 мс). Но при увеличении размера батча ONNX версия проигрывает PyTorch: bs=8 на 16.6% медленнее, bs=32 на 64.8% медленнее. Это может объясняться тем, что:
- PyTorch через sentence-transformers оптимизирован для батчевого инференса
- ONNX Runtime с enable_mem_pattern = False (нужен для динамических batch size) теряет часть оптимизаций работы с памятью
- Mean pooling и L2 нормализация в numpy менее оптимальны для больших батчей по сравнению с PyTorch реализацией в sentence-transformers

### Пропускная способность

Несмотря на проигрыш в батчевой латентности, ONNX показывает рост throughput в 2.8 раз (381.30 vs 137.11 req/s) в конкурентном сценарии с одиночными запросами, что согласуется с улучшением single-request латентности. Каждый запрос обрабатывается быстрее, поэтому при конкурентной нагрузке через систему проходит больше запросов за единицу времени.

### Потребление ресурсов

- **Время загрузки:** сократилось в 3.2 раза (3.72 с → 1.16 с). ONNX Runtime загружает граф без инициализации тяжёлого PyTorch runtime, токенизатор загружается через transformers без подтягивания sentence-transformers.
- **CPU utilization:** ONNX потребляет значительно больше CPU (353.3% vs 216.8% mean, 541.7% vs 258.6% max). Это следствие более эффективной утилизации ресурсов, тк каждый запрос обрабатывается быстрее, за то же время обрабатывается больше запросов, и ORT лучше задействует параллелизм на уровне ядер ЦПУ.
- **Memory RSS:** пиковое потребление снизилось незначительно (739.4 vs 782.3 MB, −5.5%). Экономия объясняется отсутствием PyTorch runtime и sentence-transformers в памяти; ONNX Runtime имеет меньший footprint.

### Размер модели

ONNX-файл (123.9 MB) практически равен весам PyTorch (123.1 MB), тк конвертация в ONNX сохраняет FP32 представление без квантизации. Разница в 0.8 МВ это метаданные графа ONNX.

### Общий вывод

Конвертация в ONNX даёт существенные преимущества для сценариев прода:
1. **ускорение в 1.7 раз** single request латентности (4.67 ms vs 8.14 ms median)
2. **рост throughput в 2.8 раз** при конкурентной нагрузке (381.30 vs 137.11 req/s)
3. **холодный старт быстрее в 3.2 раза** (1.16 s vs 3.72 s)
4. **пиковое потребление памяти ниже на 5.5%** (739.4 vs 782.3 MB)

Слабое место — батчевый инференс (bs=32 на 65% медленнее).
