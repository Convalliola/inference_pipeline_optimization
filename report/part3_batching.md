# Часть 3 — Динамическое батчирование (оптимизация сервинга)

## 1. Описание подхода

Динамическое батчирование объединяет несколько поступивших одиночных запросов в один батч перед инференсом, что позволяет амортизировать накладные расходы модели (tokenization, forward pass) по нескольким запросам, увеличивая throughput при конкурентной нагрузке.

### Архитектура

- **Очередь:** asyncio.Queue принимает пары (text, Future) от каждого входящего /encode запроса
- **Worker:** фоновая корутина, которая:
  1. Ожидает первый элемент из очереди
  2. После его получения собирает дополнительные элементы в течение max_wait_ms или до достижения max_batch_size
  3. Выполняет инференс батча через ONNX Runtime
  4. Возвращает результаты через asyncio.Future каждому ожидающему запросу
- **Параметры:** max_batch_size=32, max_wait_ms=50
- **Модель:** ONNX Runtime из второй части (без изменений)

### Плюсы/минусы

- **Плюс:** рост throughput при конкурентной нагрузке за счёт батчинга
- **Минус:** добавляется задержка ожидания для одиночных запросов без конкуренции

## 4. Анализ и выводы

### Латентность одиночных запросов: ожидаемая деградация

Медианная латентность одиночного запроса выросла с **4.67 мс до 58.56 мс** из-за max_wait_ms=50 ms: при последовательных запросах в очереди всегда оказывается ровно один элемент, и воркер каждый раз ожидает полный таймаут перед выполнением инференса. Фактическая задержка около 59 мс (50 мс ожидания + ~5 мс инференса + ~4 мс overhead). Это архитектурный компромисс динамического батчирования.

### Concurrent throughput: батчирование не оправдало ожиданий

Вместо ожидаемого роста пропускной способности, throughput упал с **381.30 до 136.56 req/s** (−64.2%). Можно объяснить следующим:

1. **Однопоточный worker:** единственный воркер-корутина обрабатывает батчи последовательно. Пока один батч выполняется в run_in_executor, новые запросы накапливаются в очереди, но не могут быть обработаны параллельно.
2. **Overhead ожидания:** max_wait_ms=50 ms добавляет задержку каждому батчу. При 10 конкурентных воркерах запросы поступают быстрее, чем за 50 мс, но воркер всё равно ждёт до таймаута или max_batch_size.
3. **ONNX Runtime на CPU не выигрывает от батчинга:** в отличие от GPU, где батчинг критичен для утилизации параллельных ядер, ЦПУ обрабатывает элементы батча последовательно. Батч из 10 элементов на ЦПУ занимает примерно в 10 раз больше, чем один элемент, без выигрыша от параллелизма.

### CPU utilization: резкое снижение

CPU utilization упал с 353.3% (mean) до 93.7% — снижение на 73.5%. Это прямое следствие архитектуры батчера: единственный воркер сериализует весь инференс в последовательную цепочку батчей. В отличие от ONNX без батчирования, где несколько запросов обрабатывались параллельно и задействовали несколько ядер, здесь активно используется лишь одно ядро. Это объясняет падение throughput: система не утилизирует доступные вычислительные ресурсы.

### Стабильность латентности

Положительный эффект батчирования — более стабильная латентность при конкурентной нагрузке: хотя абсолютные значения выше, коэффициент p99/median уменьшился с 2.83x (ONNX: 64.51/22.78) до 1.43x (Batched: 101.95/71.36), что означает более предсказуемое время отклика.

### Batch endpoint: без изменений

Эндпоинт /encode_batch не проходит через динамический batcher и работает напрямую с ONNX моделью, поэтому латентность батчей практически не изменилась (bs=1: 4.74 ms vs 4.85 ms, bs=8: 15.87 ms vs 16.13 ms).

### Потребление ресурсов

Memory RSS практически не изменился (721.0 vs 739.4 MB, −2.5%), тк мы добавили лишь легковесную asyncio-инфраструктуру (очередь, futures, worker task).

### Общий вывод

Динамическое батчирование в текущей конфигурации не даёт преимуществ для ЦПУ инференса по сравнению с ONNX Runtime без батчирования, потому что:

1. На CPU вычисления внутри батча идут последовательно, и общее время растёт пропорционально batch size.
2. Overhead ожидания (50 мс) критичен при малой нагрузке и доминирует над временем инференса (~5 мс).
3. Однопоточная обработка через единственного воркера не утилизирует многоядерность (CPU: 93.7% vs 353.3%).

Главный вывод: динамическое батчирование на ЦПУ не оправдало ожиданий, потому что оно не даёт параллелизма внутри батча (в отличие от ГПУ), сериализует инференс в один поток и теряет мультиядерный параллелизм, а таймаут ожидания в 50 мс доминирует над временем инференса (~5 мс).
