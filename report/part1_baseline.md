# Часть 1 — Базовый инференс

## 1. Описание модели

Подопытная модль — [sergeyzh/rubert-mini-frida](https://huggingface.co/sergeyzh/rubert-mini-frida) на 32 млн параметров

## 2. Архитектура сервиса

- **Фреймворк:** FastAPI + Uvicorn
- **Библиотека инференса:** sentence-transformers
- **Устройство:** CPU
- **Эндпоинты:**
  - `POST /encode` — кодирование одного текста
  - `POST /encode_batch` — кодирование батча текстов
  - `GET /health` — healthcheck

## 3. Обоснование выбора метрик

**Latency (p50, p95, p99, mean)**: показывает, сколько времени занимает обработка одного запроса; одна из главных метрик инференс пайплайна, потому что напрямую влияет на качество сервиса с точки зрения пользователя. Помимо среднего значения смотрим также и на перцентили, тк среднее значение может скрывать нестабильность системы:
	-	mean показывает общую усредненную картину
	-	p50 отражает типичное время ответа
	- p95 показывает, насколько часто возникают заметно медленные ответы
	-	p99 помогает увидеть редкие, но критичные просадки

**Throughput (req/s)**: пропускная способность системы при конкурентной нагрузке; показывает, сколько запросов система способна обработать за единицу времени и помогает оценить, насколько хорошо пайплайн масштабируется и какой объем нагрузки он выдерживает.

**CPU utilization (%)**: показывает, насколько активно используются вычислительные ресурсы процессора во время работы пайплайна. Замеряется во время конкурентной нагрузки (throughput-теста) в фоновом потоке с интервалом 0.5 с. Значения выше 100% означают использование нескольких ядер (psutil суммирует нагрузку по всем ядрам). Эта метрика нужна, тк улучшение latency или throughput само по себе ещё не значит, что всё хорошо, может быть, ускорение достигнуто ценой почти полной загрузки ЦПУ, что ухудшает устойчивость системы и ограничивает дальнейшее масштабирование.

**Memory RSS (MB)**: определяет требования к ресурсам для развёртывания; замеряется во время конкурентной нагрузки (mean и peak). Оптимизации могут снижать latency, но одновременно увеличивать потребление памяти, а тк память напрямую влияет на стоимость инфраструктуры (чем выше RSS, тем дороже инстанс нужен для запуска сервиса), то и метрика нам очень важна.

**Model load time (s)**: время загрузки модели при старте сервиса; влияет на время холодного старта, важно при автоскейлинге и перезапусках. Некоторые оптимизации inference pipeline (сериализация модели в другом формате, lazy loading итд) влияют именно на этап инициализации и без model load time невозможно оценить этот эффект.

## 4. Сценарии бенчмарков

1. **Single request latency** — 100 последовательных запросов с коротким текстом
2. **Batch request latency** — 100 последовательных запросов с батчами размером 1, 8, 32
3. **Concurrent throughput** — 10 конкурентных воркеров, 500 запросов суммарно
4. **Resource monitoring** — замер CPU и памяти процесса сервера во время конкурентной нагрузки

## 6. Наблюдения и выводы

### Латентность одиночных запросов

Медианная латентность одиночного запроса = 8.14 ms, для ЦПУ инференса модели на 32,3 млн параметров неплохой результат. Есть разрыв между p95 (9.27 ms) и p99 (67.20 ms), что указывает на наличие редких значительных выбросов, связанных со сборкой мусора в Python или конкуренцией за ресурсы ОС. Значение p99 совпадает с max, что говорит о единичном выбросе.

### Масштабирование по batch size

При увеличении batch size медианная latency одного вызова модели возрастает с 7.90 мс при bs=1 до 13.83 при bs=8 и 31.33 при bs=32. Рост сублинейный: при увеличении размера батча в 32 раза время выполнения увеличивается примерно в 4 раза. То есть можно сказать, что модель эффективно использует batching, тк фиксированные накладные расходы одного инференс-вызова распределяются между несколькими входными объектами. В результате медианное время обработки одного элемента внутри батча уменьшается с 7.90 мс при bs=1 до примерно 1 мс при bs=32, то есть почти в 8 раз.

Таким образом, batching существенно повышает вычислительную эффективность и должен положительно влиять на throughput.

### Пропускная способность

При 10 конкурентных воркерах сервис достигает 137.11 req/s. Средняя латентность при конкурентной нагрузке (72.60 ms) сильно выше, чем при последовательных запросах (8.85 ms), что ожидаемо, тк запросы конкурируют за ЦПУ, и uvicorn обрабатывает их последовательно в одном процессе. Для увеличения throughput можно использовать несколько uvicorn воркеров.

### Потребление ресурсов

- **CPU: 216.8% (mean), 258.6% (max)** — сервер активно использует несколько ядер ЦПУ при конкурентной нагрузке. Значения выше 100% означают использование более одного ядра (psutil суммирует нагрузку по всем ядрам), указывает на эффективную утилизацию мультиядерной архитектуры.
- **RSS: 651.3 MB (mean), 782.3 MB (max)** — существенный объём для модели размером в 32 млн параметров. Разница объясняется загрузкой PyTorch runtime, tokenizer и накладными расходами sentence-transformers.

### Время загрузки модели

Холодный старт занимает 3,72 секунды, что включает загрузку весов с диска и инициализацию токенайзера и модели. Для продакшена это значит, что при масштабировании или перезапуске сервиса стоит учитывать задержку в несколько секунд до готовности.

### Общий вывод

Базовый ЦПУ инференс rubert-mini-frida через FastAPI обеспечивает приемлемую латентность для single-request сценариев (около 8 мс) и хорошую пропускную способность (примерно 137 req/s).
